# ZXCode Product Fork Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the imported OpenCode codebase into a product-level fork named ZXCode with `zxcode` as the primary CLI command.

**Architecture:** Keep the OpenCode runtime, agent, session, model, tool, and package workspace architecture intact. Add a small product identity module, route user-facing CLI/build/config paths through it, and preserve legacy OpenCode config reads without silently rewriting user files.

**Tech Stack:** Bun, TypeScript, Effect, yargs, OpenTUI, existing OpenCode workspace packages, Bun test, tsgo typecheck.

---

## Scope And File Map

This plan implements the approved level-2 fork. It does not rename the internal `@opencode-ai/*` package scope in v1 because that would touch thousands of imports and turn a brand fork into a deep fork.

Create:

- `packages/core/src/product.ts`: central product identity constants for ZXCode plus legacy OpenCode identifiers.
- `packages/core/test/product.test.ts`: unit tests for product identity constants.
- `NOTICES.md`: MIT attribution and non-affiliation statement.

Modify:

- `package.json`: root name, repository URL, dev script names where user-facing.
- `packages/core/src/global.ts`: XDG app directory changes from `opencode` to `zxcode`; expose legacy paths for compatibility reads.
- `packages/core/src/config.ts`: prefer `zxcode` config names and `.zxcode`, then read compatible OpenCode config names and `.opencode`.
- `packages/core/test/global.test.ts`: assert new ZXCode temp path and legacy OpenCode path.
- `packages/opencode/package.json`: package name and `bin` mapping to `zxcode`.
- `packages/opencode/bin/opencode` -> `packages/opencode/bin/zxcode`: npm shim rebrand, binary resolution, and compatibility env fallback.
- `packages/opencode/script/build.ts`: compiled binary and release artifact names.
- `packages/opencode/Dockerfile`: installed binary and entrypoint.
- `install`: installer app name, fallback bin directory, download repo, executable names, and final instructions.
- `packages/opencode/src/index.ts`: yargs script name, logo/help filtering, process env markers.
- `packages/opencode/src/cli/cmd/run.ts`: user-facing command descriptions for `zxcode`.
- `packages/opencode/src/cli/cmd/run/splash.ts`: entry title and resume command.
- `packages/opencode/src/cli/cmd/uninstall.ts`: uninstall prompts, package manager commands, shell cleanup markers.
- `packages/tui/src/app.tsx`: terminal title and visible product name in TUI notifications.
- `README.md` and `README.zh.md`: GitHub-facing ZXCode README with install, usage, attribution, and upstream notes.
- `packages/opencode/test/cli/help/help-snapshots.test.ts`: snapshot names and comments for `zxcode`.
- Snapshot files generated by `bun test` for help output, if Bun updates them in place.

Reference but do not rename in v1:

- `@opencode-ai/*` imports and workspace package names.
- Provider IDs named `opencode`, such as the OpenCode-hosted provider.
- Internal HTTP headers such as `x-opencode-directory`; these are protocol identifiers, not product marketing strings.
- Existing tests that exercise OpenCode provider behavior.
